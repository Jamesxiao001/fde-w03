# 青禾指标构建方法

## 一、目标与输入
按输入 targets 的 ID 逐项处理，不新增、不改名、不遗漏、不合并名称相近的目标。各输入的职责：business_model 提供业务对象、对象之间的关系、判定单元，以及经访谈确认的业务规则及其适用范围；materials 中的报表说明、财务邮件、运营周报和统计确认邮件提供每个报表项目的统计口径、分子分母、时间归属和查询限制；数据字典提供实际表名、列名、取值和单位；access_tables 只说明物理列，不提供业务公式；dimension_targets 只列查询目标，不提供连接实现。

处理每个目标前先判断属于哪种情况：材料给了定义且字段齐全；材料给了定义但字段或关系不清；材料没有定义；材料之间说法不一致。只有第一种才能生成定义，其余按第五段处理。字段存在不等于业务上应计入；不得凭指标名称、字段名称或行业常识推断口径，不得加入输入没有提出的条件。

## 二、候选及依据
为每个目标整理以下事实，每一项都要在输入中找到依据：统计对象（订单、账户、门店、账户×月等）与行粒度；统计时间及归属日期；计入与排除条件；金额或数量的构成（计入项、扣减项）；聚合方式（求和、计数、去重计数）；单位；零分母、覆盖内无数据、覆盖外三种情况分别怎样表达；查询限制。

多个指标共用的基础概念（例如“有效订单”“购买会员”）先在材料中找到唯一定义，所有引用它的目标使用同一表达，不在各指标里各写一版。

catalog.sources 使用输入中的文件名和逐字连续的原文 quote，quote 必须能支持该定义；不把两段话拼成一句，不把自己的解释写成引用。来自业务模型的规则同时记入 business_model_usage，quote 为业务模型原文。材料先后、措辞强弱不能自动裁决分歧；业务模型对某条规则写明了“适用范围”或“确认对象”的，按其适用范围使用。

## 三、字段与计算转换
先确定表达式作用于哪种行，再映射字段。行级表达式只使用数据字典中存在的列名，逐字照抄；展示用的中文名与物理列名分开。计入与排除条件写进表达式（不满足条件时取 0 或 NULL，按聚合方式选择）。金额类指标逐项核对计入项与扣减项；“原价减实付”“实付减退款”等构成必须与材料原文一致。

聚合方式与统计对象一致：订单数按订单计；“不同账户数”“不同门店数”用去重计数，去重对象是材料指明的对象；人均、单均、频次、占比、率等用 ratio 类型，分子分母分别引用已定义的指标，而不是对逐行比率求平均。去重只能修复重复的标识，不能修复被重复累加的金额，遇到可能放大行数的关联先按第六段处理。

材料把某个日期定为归属日期（例如退款按原订单日期归属）时，该指标的统计时间使用该日期列，不使用其他日期，也不推测数据中不存在的日期字段。

## 四、依赖与输出协议
只返回一个 JSON 对象，包含 semantic_models、metrics、catalog、model_sql、grain_keys、unresolved、business_model_usage，不返回 Markdown、YAML 或解释文字。按 native_format 与 contract 的写法输出，使用 semantic_models/measures 旧格式，兼容 MetricFlow 0.213.0。

simple 指标通过 type_params.measure 引用 measure；ratio 指标的 numerator 与 denominator 引用本次输出中已定义的指标 ID。measure 名称全局唯一。输出前检查每个指标的依赖都在本次输出内闭合，依赖缺失的指标列入未决。

catalog 只收录已定义指标，每项给出 id、name、aliases、unit、constraints、sources、query_policy。unit 按指标量纲选择明确标识：金额 cents，人数与单数 count，商品件数 items，比率与占比 ratio，金额／单 cents_per_order，金额／账户 cents_per_member，单数／账户 orders_per_member，件数／单 items_per_order；分子分母的量纲要与 unit 一致。材料要求只按完整自然月、全门店或全渠道查询的指标，query_policy.full_month_only 设为 true，并在 constraints 中写明限制；其余为 false。限制不能只写在 description 里。

## 五、未决、冲突与修订
材料缺少某目标的定义、所需字段或关系不清、或材料之间对同一范围说法冲突时，把该目标列入 unresolved：metric_id 用真实目标 ID，missing_facts 写缺哪条事实，reason 写影响哪部分计算、应向哪位业务模型或材料中已出现的负责角色核实什么问题；不知道负责人时写“请项目对接人确定”，不编人名。维度缺少关系依据时以 dimension_id 列未决。

尤其注意资格、端点、计入范围类规则：业务模型或材料没有明确写出时，不得用常见习惯、数据库默认比较或字段名代替（例如不能自行决定日期端点是否包含当天、哪些产品计入），必须列未决。每个目标只能出现在已定义或未决其中一边，不为清空 unresolved 补写条件。不要把构建检查结果或自己的推断写成客户事实。

## 六、语义模型与派生模型
从业务对象出发建模，而不是把每张表机械复制成一个模型。依次完成：
1. 列出目标涉及的业务对象及其角色，写明每个模型一行代表什么、来自哪张接入表或派生 SQL。
2. 关系映射到实体：被关联一侧的键必须唯一且非空；方向从多的一侧（foreign）指向唯一的一侧（primary）。同一物理表在不同关系中承担不同角色时（例如订单的成交门店与账户的归属门店），分别建立语义模型和实体名，二者可引用同一接入表。
3. 属性映射到维度。逐项核对 dimension_targets：实体查询 ID 对应实体名，属性查询 ID 为“主实体名__局部维度名”，因此实体名要与目标 ID 的前缀一致；dimensions[].name 只写局部名。确实缺少关系依据时列未决，不凭空连接。
4. 每个有统计时间的模型在 defaults.agg_time_dimension 中引用一个真实日期列。

判断是否需要派生模型：指标的统计对象不是接入表的一行，或计算必须分阶段完成时，先生成派生 SQL，再为结果建语义模型和指标。三类常见多阶段规则：
- 排序（如“首次”“第二笔及以后”）：先按材料核实排序对象、参与排序的记录范围、排序依据及相同时的次序、排序所用的历史范围；在材料指定的完整历史上排序得到序号，再按统计窗口筛选，不能让查询窗口改变历史顺序。
- 按期汇总（如“同一自然月至少一笔／两笔”）：先汇总到“对象×期间”粒度，每个对象每期最多一行，再在该粒度上判断和计数；期间日期列用非保留名。
- 资格判断（如判定时点是否具备某种资格）：按业务模型核实判断对象、判定时点、事实来源表、计入范围、有效期端点、多条记录重叠时的处理和空值含义；先得到“对象×判定时点”的判断结果，每个对象每个时点最多一行，再接回同粒度的汇总。判断只需“是否存在一条满足条件的记录”时用 EXISTS 或先聚合到对象粒度，不把多条明细行带回主体，避免重复计人或重复累计金额。规则中任一项未确认，相关目标列未决。

先汇总再关联：一对多关系先收敛到需要的粒度，再与主体连接；汇总键要保留后续需要的维度。每个语义模型在 grain_keys 中给出实际粒度列名列表，组合粒度逐列列出，不写 SQL 表达式，不用拼接键逃避检查；人为生成的连接键不能代替对真实组合列的声明。

SQL 只用 SELECT／WITH 和 {{ ref('模型名') }}，model 字段写 ref('模型名')；派生模型名为合法小写名，不与 members、stores、cards、orders、time_spine 重名；不使用文件、网络、DDL 或 DML。

原生配置约束：一个实体名只能有一个 primary／unique 目标，其他关联用 foreign；同一主实体与维度名的配对全局唯一，派生表与原表表示不同行集合或粒度时，为派生表声明自己的主实体名，不复制原表的主实体与时间维度配对。metric_time 以及 day、week、month、quarter、year 等时间粒度词是保留名，不能作为实体或维度名；metric_time__day、metric_time__month 只作查询目标 ID。任何有 dimensions 的模型必须声明 primary 实体。输出前逐项检查这些约束。
